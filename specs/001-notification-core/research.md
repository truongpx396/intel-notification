## 4. Provider fallback strategy (one-hop)

- **Decision**: LLM aliases (`fast`, `smart`, `embed`, `rerank`) resolve to `{primary, fallback}` (plus multi-key/deployment load-balancing) in the **standalone LLM gateway** (LiteLLM router config, Bifrost-swappable — §21), **not** in application code. Fail over on timeout / 5xx / rate-limit only, capped at one hop, with an `llm.fallback.count` metric and a circuit breaker. `embed` has **no per-call fallback**: the `embed` alias is pinned single-model (no fallback route), and a down primary embedder parks the chunk in `ingestion.dlq` for retry rather than embedding with a different model.

## 10. Redis role separation (single cluster, logical split)

- **Behavior under Cluster / failover** (why scaling Redis is safe): a `SET NX` lock is **not** a correctness primitive under async-replication failover — a primary can ACK the lock, die before replicating, and a promoted replica grant it twice (the standard Redlock critique). The design never relies on it: every Redis guard has a Postgres backstop (`credit_ledger.idem_key UNIQUE`, notifications `(user_id, idem_key) UNIQUE`, the janitor's conditional `UPDATE … WHERE status='running'` fencing claim — §15), so a two-leader failover window produces zero duplicate effects. Four residual *scale* (not correctness) requirements when moving to Redis Cluster: (a) **hash-tag a workspace's keys** (`credit:{ws}:balance`, `billing:applied:{ws}:{idem}`) so they colocate on one slot and stay atomically scriptable across slots; (b) the hot `DECRBY` balance is a **cache** — a lost decrement on failover is a temporary-overspend/RPO question corrected by the hourly reconcile, never a double-charge; (c) rate-limit/budget counters **and** the opaque session store are Redis-only and **fail-safe** (a failover lets a few extra ops through / logs users out — best-effort, not a money or security hole); (d) **SSE fan-out pub/sub does not survive naive Cluster mode** — plain `PUBLISH`/`SUBSCRIBE` is broadcast across the *entire* cluster bus to every node, so the streaming hop (the host's streaming tier) must move to **sharded pub/sub** (`SPUBLISH`/`SSUBSCRIBE`, Redis 7+) keyed by a **slot-hash-tagged `stream_id`** (`{stream}:<id>`) so a token reaches only the relay replicas on that shard. Because any relay replica already serves any `stream_id` with no sticky sessions (§14), this is a keying change, not a topology change — but it is the same decision as the SSE-relay split, so the two are one workstream ([ROADMAP.md](../../ROADMAP.md)), not two phases. Verifying reconciliation + rehydration across failover is [ROADMAP.md](../../ROADMAP.md).

## 14. Scale-forward seams locked in Phase 1 (rework-risk decisions)

- **NATS = JetStream, durable pull consumers, per-subject queue groups (not core NATS).** Crash recovery, DLQ redelivery, and autoscale-on-consumer-lag all assume persistent streams + durable consumers. Core NATS would lose in-flight messages on a worker crash and leave no lag metric to scale on — unfixable without rewriting every publisher/consumer. Queue groups make adding pods pure horizontal scale-out. (§6, [contracts/bus-subjects.md](./contracts/bus-subjects.md))
- **Scheduled & background work runs single-owner in a dedicated `cmd/worker` role, never inside a request-serving tier.** Periodic jobs (outbox drain, hourly reconcile, stale-heartbeat janitor, DLQ sweeps, `llm_cost_daily` matview refresh) are triggered by an external CronJob → NATS tick → JetStream queue-group consumer, and every action is an idempotent atomic claim — so adding `api`/`relay`/`worker` replicas can never double-fire a timer. Embedding these loops in `cmd/api` now would make Phase 4 autoscaling silently multiply them (N concurrent reconcilers/janitors); extracting them later means re-homing every job. (§15)

## 15. Scheduled & background work — single-owner execution (no duplicate timers)

- **Decision**: No scheduled or background loop runs inside a request-serving tier. All periodic/background work — credit-outbox drain, hourly reconciliation, `agent_run` stale-heartbeat janitor, DLQ retry sweeps, and the `llm_cost_daily` matview refresh — runs in a dedicated **`cmd/worker` role** (same Go image as `cmd/api`/`cmd/relay`, role-selected at deploy; §14), with the Python stale-heartbeat janitor likewise deployed as its own single-owner role rather than a loop inside every `long_horizon` pod. Scheduling is **external and event-driven** — a pluggable scheduler (Kubernetes `CronJob`, DigitalOcean App Platform scheduled component / Function, or a plain `cron`/systemd timer on a Droplet; locally a Make target or a single in-process ticker in the one `worker`) emits a NATS JetStream tick (`billing.reconcile.tick`, `agent.janitor.tick`, `usage.matview.refresh`). The “no in-process `time.Ticker`” rule applies to the **request-serving tiers** (`api`/`relay`); the single-owner `worker` MAY use an internal ticker, since correctness rests on the atomic claim below, not on the trigger. Each tick / outbox / DLQ subject is consumed by a **durable queue group → exactly one worker handles each event**, with JetStream redelivery on crash. Correctness never depends on “only one replica is running”: every scheduled action is an **idempotent atomic claim**, so a duplicate delivery is a no-op — the janitor re-queues only via a conditional transition (`UPDATE agent_run SET status='queued' WHERE id=$1 AND status='running' AND last_heartbeat_at < $2 RETURNING id`), reconcile guards each hour-bucket with `SET NX reconcile:lock:{shard}:{hour_bucket}`, and the outbox uses an atomic pop (`LPOP` / Stream consumer-group) plus `credit_ledger.idem_key UNIQUE`. The matview refresh uses `REFRESH MATERIALIZED VIEW CONCURRENTLY` (requires a UNIQUE index) so a duplicate tick is at worst redundant work, never a lock error.

## 18. Dead-letter drain & poison-message handling — bounded re-drive, then terminal park

- **Decision**: Every DLQ subject (`ingestion.dlq.<ws>`, `notify.email.dlq.<ws>`, and any future `*.dlq.<ws>`) is drained by a single **generic DLQ sweeper** that runs single-owner in `cmd/worker`, triggered by an external `dlq.sweep.tick` (the same pluggable scheduler seam as §15) and consumed by a durable queue group → exactly one worker per tick. Each parked message carries a `dlq_attempts` counter and a `first_failed_at`. For each message the sweeper either (a) **re-drives** it — if `dlq_attempts < MAX_DLQ_ATTEMPTS` (default 5) and an exponential-backoff window keyed on `first_failed_at` has elapsed, it re-publishes the message to its **original work subject** (the embed step for `ingestion.dlq`, `notify.email.<ws>` for the email DLQ) with `dlq_attempts+1`, so the **owning tier reprocesses it** (Python re-embeds with the *original* model only, §4; the Go email worker re-sends) — or (b) **terminally parks** it — once `dlq_attempts ≥ MAX_DLQ_ATTEMPTS`, it writes the message to a durable `dead_letters` Postgres table (queryable by admins for inspection / manual replay) and emits a `dlq.dead.count` metric for alerting; the message is never re-driven again.
- **Why re-drive to the live subject, not reprocess inside the sweeper**: the sweeper is a generic Go mover that knows nothing about embedding or SMTP. Re-publishing to the original subject keeps the actual retry in the tier that owns it (Python embed / Go mailer) and reuses that worker's existing idempotency — chunk identity for embeds, and the email worker's "mark sent only after provider-accept" rule — so a re-drive of a genuinely-unsent item delivers exactly once while a duplicate is a no-op. Same separation as §15: *who schedules* (cron tick) vs *who executes* (owning worker) vs *what guarantees correctness* (data-layer idempotency).
- **Why a hard attempt cap**: without a terminal state a poison message (malformed payload, permanently-rejecting recipient) loops forever, burning provider calls and masking the failure. `MAX_DLQ_ATTEMPTS` + the `dead_letters` table converts an unbounded retry into a bounded, observable, replay-on-demand outcome — "never dropped" becomes "either recovered or visibly dead," not "retried indefinitely." For email specifically, hard bounces/complaints short-circuit even earlier via `channel_suppressions` ([D13](design-decisions.md#d13)), so the cap mainly catches transient-looking-but-permanent failures.
- **Alternatives considered**: (a) JetStream `MaxDeliver` + a native DLQ only (no sweeper) — rejected: gives in-stream redelivery but no *cross-outage* re-drive (a message parked after `MaxDeliver` just sits), no backoff control, and no queryable terminal store. (b) Per-pipeline bespoke retry loops — rejected: duplicates backoff/cap/poison logic in every worker and re-tier-couples the sweeper. (c) Infinite re-drive with alert-only — rejected: a poison message loops forever and the alert never clears.

## 23. Notification fan-out durability — transactional outbox (crash-safe multi-channel delivery)

- **Decision**: The notification service does **not** deliver channels inline. On a `notify.<ws>` event it resolves preferences and, in **one Postgres transaction**, writes the `notifications` row **and one `notification_outbox` row per enabled channel** (`UNIQUE(notification_id, channel)`), then acks. A separate **Dispatcher** (queue-group consumer in `cmd/worker`) drains `notification_outbox` **at-least-once**, delivering each entry through its channel (in-app → Redis pub/sub `notify:user:<id>`; email → `notify.email.<ws>` → `kernel/mailer.go`), marking `delivered_at` or bumping `attempts` under backoff and parking in `dead_letters` after `MAX_DLQ_ATTEMPTS` (§18). The Redis `SET NX notify:applied:{idem_key}` guard is a **fast pre-check on the durable write only** — never on delivery. Correctness rests on `notifications.(user_id, idem_key) UNIQUE` + per-channel outbox uniqueness, not on the ephemeral Redis guard.
- **Why the inline design is unsafe**: the naive handler does `INSERT` + in-app publish + email enqueue as three **non-transactional** side-effects, gated by a `SET NX` that short-circuits the *entire* handler on a duplicate. If a replica sets the guard, commits the row, then crashes *before* the email enqueue, the JetStream redelivery hits the guard and skips — the email is **silently lost**, violating NS-002 ("one email") and NR-011 ("parked … rather than dropping silently"). The outbox makes the durable row and the delivery intents commit **together**, so recovery always has a queued intent to drive.
- **Why this mirrors billing (§3)**: the same two-store problem — a state change must touch Postgres *and* an external side-effect that cannot share the DB transaction. Billing solved it with the Redis `DECRBY + LPUSH` outbox + single-owner drain; notifications solve it with a Postgres transactional outbox + Dispatcher drain. Both make the **durable write the source of truth** and the Redis guard a mere fast-path optimization (the Redlock caveat, §12: the guard is never the correctness primitive). The reusable `Channel` seam factors in-app + email into two swappable implementations ([notification-ports.md](contracts/notification-ports.md)).
- **Interactions**: the in-app "live badge" over Redis pub/sub stays **at-most-once** (a missed publish is cosmetic) because the unread count is always recomputable from the store and reconciled on SSE (re)connect (NR-024) — the outbox guarantees the *durable* inbox row + email, not the live nudge. Coalescing (NR-014) batches outbox entries within a window before dispatch. The `notify.email.<ws>` subject + email worker are **unchanged** — they become the transport the Dispatcher drives.
- **Alternatives considered**: (a) inline delivery + `SET NX` short-circuit (the earlier sketch) — rejected: loses a channel on a mid-handler crash. (b) ack only after all side-effects, no outbox — rejected: still loses the in-app/email work if the process dies after the DB commit but before the sends, and re-running the whole handler on redelivery re-does pref resolution and risks partial double-send with no per-channel state. (c) two-phase commit across Postgres + Redis + SMTP — rejected: no XA across these stores, and the outbox gives the same guarantee far more simply.
